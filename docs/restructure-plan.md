# 重构计划：从"知识库"到"能照着走的手册"

> **状态**：已商定，执行中 · **最后更新**：2026-10-07

## 1. 为什么要重构

第一版内容质量不错：每条建议有出处，分歧并列写出，检查清单实用。但读起来"有点奇怪"，根源是**三个不同的维度被混成了一棵树**：

- **研究套路**（这个项目靠什么逻辑产生知识）：工程研究、综述、复现……
- **研究方法**（具体怎么收集和分析证据）：问卷、访谈、对照实验……
- **学科规矩**（这个社区特有的要求）：会议文化、伦理审批、考古发掘规范……

由此带来的具体问题：

1. **拿着题目的新手进不去。** 从"我想研究 X"到"我要证明什么、该用哪种研究"，这一步没有任何章节教。
2. **同一个核心思想散落五处、用了五套分类**（OECD 三类、Shaw 问题—结果表、Brooks 三层、Shaw 三种主张、工程研究五维度），读者分不清哪个是主线。
3. **通用方法挂在计算机目录下**，42 种研究类型不在同一层级。
4. **"通用篇"其实带着计算机和机器学习口味**，人文社科读者用不上。
5. **引用拼接成了写作方式**，正文是"某某认为……某某说……"，综合后的指导反而被标成次一等的 `[本项目分析]`。
6. **广度先于深度**：32 个学科同时铺开，难以审阅。

## 2. 设计原则

1. **主线按新手的研究历程组织**，从模糊兴趣走到发表；套路、方法、学科规矩作为参考层，需要时链接过去。
2. **三个维度分开放**，不再混在一起。
3. **0→1 的问题结构是通用的，怎么做、什么算够是学科化的。**
4. **结构按通用设计，内容先写计算机。** 目录、术语、套路按所有学科都能用的方式设计；例子和具体做法先用计算机，章首注明"本章以计算机为例"。只适用于实证研究的内容单独成节、标明适用范围，以后其他学科在旁边补充，不用推倒重写。
5. **以完整的研究任务作为文件边界**，不为将来的 Auto-Research 提前拆碎。
6. **不做独立案例**，在正文里举简短的计算机例子。不同章节可以复用同一个题目（如"大模型与智能合约安全"），让读者看到一个问题在各阶段怎么推进，但不编造完整的项目故事。

## 3. 写法

**说人话，引导读者把事情想清楚、做清楚。**

- **用第二人称，从读者此刻的困惑开始**，而不是从概念定义开始；
- **先给做法，再说为什么**；
- **每节给一个"写下来"的小练习**，让读者产出具体的东西；
- **正文写综合后的指导，出处退到脚注**，正文不出现"某某认为"的拼接；
- **"不同的看法"只保留会影响操作的分歧**；
- **`[本项目分析]` 标在段落或小节层面**，不逐句标注（这是对 `CONTRIBUTING.md` 现行规则的修改，待团队确认）。

**分层规则：**

- **套路**讲"产生什么知识、需要什么证据、常用哪些方法、哪些学科常用"；**方法**讲"具体怎么做好"。一个方法可以服务多个套路。
- **方法放在哪里**：两个及以上学科使用的方法放 `06_methods/`；只有一个学科使用的实践放该学科的 `practices/`。
- **学科篇只写学科特有的内容**，通用方法一律链接到 `06_methods/`。

## 5. 八种研究套路

一个项目按**主要主张**归入一种套路，其他贡献作为次要部分。

| 套路 | 产生的知识 | 典型主张（计算机例子） |
|---|---|---|
| 观察描述 | 现象是什么样的 | "大模型生成的合约中，四成有重入漏洞" |
| 测量 | 某个东西怎么测才准 | "现有评测集存在数据泄露，新评测集更可靠" |
| 比较评估 | 已有做法中哪个更好 | "在真实合约上，工具 A 的检出率高于 B" |
| 解释因果 | 为什么会这样 | "提供漏洞模式提示会提高检出率" |
| 构建改进 | 一个更好的东西 | "新方法多发现三成漏洞" |
| 综合 | 已有知识的整体图景 | "该方向的研究可归为四类，存在三个空白" |
| 证明 | 形式上必然成立的结论 | "在条件 C 下，该算法一定终止" |
| 解读论证 | 对文本、制度、思想的新理解 | （人文社科为主，计算机阶段只留占位） |

这张表不是最终分类，在写主线和计算机篇时继续检验。
