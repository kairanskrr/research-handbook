# 收敛成项目

> 本章的道理适用于各学科，例子和具体做法以计算机为例。

## 你现在在哪里

你从[判断和筛选](04_judge-and-screen.md)出来，手里有两到四个候选。它们都过了初筛，有的还动手探索过。比如"评测集泄露"那条，你已经搜到几份公开出现过的评测合约，写出了一个初步的假设。

但你还说不清：这个项目到底要做什么、做到什么程度算完、为什么值得做。

## 这一阶段要解决什么

把一个模糊的想法，收敛成一个**站得住的项目**。具体来说，是能回答下面六个问题：

1. 我最后要证明哪句话？
2. 它值得做吗？
3. 别人做过了吗？我和最接近的工作差在哪？
4. 拿什么让人相信？
5. 我做得出来吗？
6. 以上这些，能不能写成一页纸，并经得起导师追问？
7. 可以进入第二部分了吗？我要做的是哪一类研究？

## 这一章怎么用

前六个问题**不是按顺序走一遍就完的**。它们互相牵连：

- 想到一个好结论 → 查文献发现别人去年做了 → 回到第 1 步换个角度；
- 结论想清楚了 → 发现需要的数据拿不到 → 回到第 1 步把结论改小；
- 数据有了 → 发现能证明的只是一个很弱的结论 → 回到第 2 步重新判断值不值得。

所以你会在这几步之间来回走好几轮。每一轮结束时，把结果写进一页项目简介（第 6 节）。简介写得出、改得动、导师挑不出大毛病时，这一阶段就完成了。

一般要几轮？没有标准答案。几周内来回三五轮很正常 `[本项目分析]`。如果一两个月还在原地转，见文末"回退信号"。

## 1. 写出你想证明的那句话

**先别急着想"用什么方法"，先回答：如果这个项目做成了，论文标题下面最重要的那句结论是什么？**

很多人第一次会写成"我们研究了大模型在智能合约安全中的应用"。这句话说的是你**做了什么**，而不是你**发现了什么**，读者看完不知道该相信什么。说明你的工作带来了什么时，要用表示结果的说法，而不是"研究了""探索了"这类只表示活动的说法[^shaw2003writing-e18]。

换成结论的写法，可以是：

- "现有大模型漏洞检测的高准确率，有很大一部分来自评测集的数据泄露。"
- "给大模型提供漏洞模式提示，能明显提高重入漏洞的检出率。"
- "我们的新方法在真实合约上比现有工具多发现三成漏洞，误报更少。"

三句话的话题相同，要做的事却完全不同：第一句要证明泄露存在，并展示去掉泄露后结论怎么变；第二句要做对照实验；第三句要实现一个新方法，再和现有工具比较。**结论不同，研究就不同。** 这三句分别属于"测量""解释因果""构建改进"三种研究套路，见[核心术语](../00_start-here/key-concepts.md#研究套路)。

**再看看这句话说得有多满。** 把结论拆开，看每一部分属于哪一种[^shaw2003writing-e16]：

| 说法 | 例子 | 需要的证据 |
|---|---|---|
| 说"总是""所有" | "对所有合约都有效" | 往往需要证明，实验很难支撑 |
| 说"在某条件下，提升多少" | "在 Solidity 合约上检出率提高 20%" | 在明确条件下的评估 |
| 说"存在""能做到" | "大模型能发现静态分析工具漏掉的漏洞" | 有时几个真实例子就够 |

新手最常见的是把话说得太满。说得越满，需要的证据越多。这一步常常会让你把结论改写得更准确；越早改，后面的研究越容易围绕一个能被证明的结论来规划[^shaw2003writing-e17]。

**写下来：** 写出两三个候选结论，每个一句话。不要写"研究了""探索了"。写不出来也没关系，写出最接近的一句，后面几节会帮你修改。

## 2. 它值得做吗？

有了候选结论，问自己：**就算这句话被证明了，有谁在乎？**

几个具体的问法：

- **最好的情况下，收益有多大？** 是某个指标提高一点点，还是改变大家做这件事的方式[^schulman2020opinionated-e10]？
- **如果另一个组发表了这篇论文，你会兴奋地去读吗[^olah2021taste-e11]？** 这是一个很好用的检验：你自己都不想读的论文，审稿人大概也不想读。
- **半年、一年、四年后看，它还值得吗[^eisnerproblems-e7]？** 大模型方向变化很快，今天的热点，一年后可能已经没人关心。
- **它有没有可行的攻克途径？** 意义再大，不知道从哪里下手，也不算一个好问题[^hamming1986you-e2]。

用上一节的例子试一下：

- "现有结果被数据泄露高估"：如果成立，会让整个方向重新审视已有结论，影响面广。
- "新方法多发现三成漏洞"：有价值，但要看现有工具的问题是否真的卡住了实际使用。如果大家不用现有工具是因为误报太多，那多发现漏洞就不是关键，降低误报才是。

第二个例子说明，判断重要性常常会反过来**改写你的结论**。这正是收敛的意义。

**写下来：** 对每个候选结论，用一两句话写出"如果它成立，谁会因此改变什么做法或看法"。写不出来的，先放到一边。

## 3. 别人做过了吗？

**这一步要现在做，不要等到项目做完。** 最糟的情况，是做完整个项目才发现别人早已发表了同样的工作[^noble2023ten-e5]。

**怎么查：**

1. 用你的结论里的关键词搜，找出最接近的三到五篇论文。顺着它们的参考文献往前找，再看谁引用了它们。找文献的具体做法，见[进入领域、探索文献](01_enter-a-field.md)。
2. **问懂行的人。** 文献检索总有漏掉的，导师、师兄师姐、同方向的人常常一句话就能告诉你"这个某某组去年做过"[^eisnerproblems-e4][^eisnerproblems-e9]。
3. 计算机方向更新快，除了正式发表的论文，还要查预印本网站和近期会议的录用列表 `[本项目分析]`。

**然后画一张对比表。** 不要只写"已有很多相关研究"，而是具体写出每项工作做到了什么、有什么限制，以及你在哪一点上不同。Shaw 举过一个好例子：A 方法达到 60% 覆盖率；B 方法达到 80%，但只适用于没有指针的情况；我们的方法达到 90%，并放宽了这个限制[^shaw2003writing-e3]。

| 最接近的工作 | 它做到了什么 | 它的限制 | 我的不同 |
|---|---|---|---|
| 工作 A | | | |
| 工作 B | | | |
| 工作 C | | | |

**如果发现别人已经做过了**，先别急着放弃 `[本项目分析]`：

- **完全一样**：换题，回到[生成候选问题](02_generate-problems.md)。
- **对方只做了一部分**：比如只在一个数据集上验证、只考虑了一类漏洞，你的结论可以针对它没覆盖的部分。
- **对方的做法有问题**：比如评测有泄露、基线太弱，那么"指出并修正这个问题"本身就可以是一个结论。

把问题稍微换个提法，常常就能找到更好的切入点[^hamming1986you-e13][^eisnerproblems-e10]。

**写下来：** 填好上面的对比表。"我的不同"一栏如果写不出具体内容，说明这个结论还不够新，回到第 1 节修改。

## 4. 拿什么让人相信？

结论有了，接下来想：**一个持怀疑态度的审稿人，要看到什么才会相信这句话？** 读者凭什么相信你的结果？应该用什么标准衡量你的结论？什么具体证据能表明你做到了[^shaw2003writing-e6]？

**证据由结论决定，而不是反过来。** 不要先想"我可以做什么实验"，再去找它能说明什么。

用"评测结果被数据泄露高估"这个例子，审稿人至少会追问：

| 审稿人会问 | 需要的证据 |
|---|---|
| 泄露真的存在吗？ | 评测集中有多少合约出现在模型的训练数据里，怎么确认的 |
| 泄露真的影响了结果吗？ | 去掉泄露样本前后，同一批工具的准确率对比 |
| 是不是只有个别工具受影响？ | 多个模型、多个工具上的结果 |
| 你的判断方法可靠吗？ | 判断"是否泄露"的方法本身的准确性 |

**一个很有用的办法：先画出空的结果表。** 实验还没做，也可以把论文里的结果表画出来：行是什么、列是什么、每一格要填什么数字[^eisnerfirst-e5]。诚实地画出来，常常会发现要证明你的结论，需要的工作比预想的多[^eisnerfirst-e6]。越早发现越好。

如果某个结论怎么也想不出该用什么证据支撑，要么改写它，要么删掉它 `[本项目分析]`。

具体怎么设计实验、怎么选基线和评测集，是下一阶段的事，见[从研究问题到证据清单](../02_do-the-project/01_question-to-evidence.md)。这一步只需要想清楚**需要什么证据**，不需要设计出**怎么拿到**的全部细节。

**写下来：** 对你的核心结论，列出审稿人会追问的三到五个问题，并画出至少一张空的结果表。

## 5. 你做得出来吗？

到这一步，你可能已经有了一个漂亮的结论和一份清楚的证据清单。最后要问：**以你现在的条件，能拿到这些证据吗？**

计算机方向常见的卡点 `[本项目分析]`：

| 要确认的 | 例子 |
|---|---|
| 数据 | 有没有现成的漏洞数据集？标注质量如何？要自己标注的话，要多少人力？ |
| 算力和接口 | 需要调用多少次商用大模型接口？费用能否承担？本地部署需要多少显卡？ |
| 基线 | 要比较的现有工具能不能跑起来？开源吗？ |
| 评测 | 有没有公认的评测集？如果要自己建，建评测集本身可能就是一个项目 |
| 技能 | 你会不会写智能合约、懂不懂相关的分析工具？要学多久？ |
| 时间 | 离你的目标投稿截止日期还有多久？ |
| 伦理 | 如果会在真实部署的合约上发现漏洞，要先私下告知负责方，再公开，见[计算机学科概况](../07_fields/computer-science/README.md#伦理问题有本领域的特点) |

**对可行性的估计要打个折扣。** 纸面上看起来容易的问题，实际往往很难；纸面上看起来难的，实际几乎做不成[^alon2009choose-e3]。完成时间取决于你的技能和条件，不是别人的[^alon2009choose-e2]。刚开始做研究时，选一个容易些的问题更好，能更快得到正反馈[^alon2009choose-e7]。

**找一个最便宜的办法，先试一下最没把握的部分。** 不是每个想法都能成，设计一个小实验尽快验证核心假设，要失败就快点失败[^huang2023decide-e5]。例如：

- 担心泄露检测方法不可靠：先手工检查 50 个样本，看判断准不准；
- 担心新方法没有效果：先在 20 个合约上手工试一下提示，看大模型能不能发现问题；
这个小实验可能只要几天，却能省下几个月。怎样把它设计得小而快，见[动手探索](03_explore.md#2-设计小而快的探索)。

**写下来：** 列出你的项目需要的每样东西，标出"已有 / 能拿到 / 不确定"。对最不确定的一项，写下你打算用什么小实验在一两周内弄清楚。

## 6. 写成一页项目简介，并反复修改

把前五步的结果写在一页纸上。这一页就是你和导师讨论的依据，也是你自己判断"想清楚没有"的标准。

> **我要回答的问题是：**____
>
> **我希望证明的核心结论是：**____（一句话，用表示结果的说法）
>
> **它重要，因为：**____（谁会因此改变什么）
>
> **最接近的已有工作是：**____；**我的不同在于：**____
>
> **它属于哪种研究套路：**____
>
> **要让人相信，需要这些证据：**____
>
> **我能拿到这些证据，因为：**____（数据、算力、基线、技能、时间）
>
> **最没把握的部分是：**____；**我打算这样先试：**____

**写不出来的栏目，就是你现在最该想清楚的地方。** 不要硬填。

**写好后，给导师或懂行的同学看。** 问他们：这个结论站得住吗？是一个重要且还没解决的问题吗[^noble2023ten-e10]？如果他们觉得基本想法会让审稿人怀疑或觉得无聊，最好在花时间之前就知道[^eisnerfirst-e3]。拿不准几个候选结论选哪个时，可以请导师给每个打分，对分歧大的深入讨论[^olah2021taste-e4]。

**每一轮修改，都更新这一页。** 不要另起一份。保留旧版本，几个月后回头看，你会清楚地看到自己的想法是怎么变化的。

**写下来：** 写出一页项目简介，给导师看，记下导师的追问和你的修改。

## 7. 出口：可以进入第二部分了吗？

第一部分到这里结束。进入第二部分之前，做一次出口检查 `[本项目分析]`：

| 出口检查 | 怎样算过 | 没过，回到哪里 |
|---|---|---|
| 一句写得下的具体假设 | 能用一句表示结果的话写出核心结论，别人读了知道你要证明什么 | 第 1 节；怎么也写不出来，说明还在探索，回到[动手探索](03_explore.md) |
| 知道拿什么证据检验 | 画出了空的结果表，知道每一格要填什么 | 第 4 节 |
| 知道最大风险在哪 | 说得出最可能让项目失败的一件事，并且用小实验试过 | 第 5 节 |
| 导师认可 | 导师看过一页简介，没有根本性的反对 | 第 6 节 |

前两条合起来，就是进入检验阶段的标志：能写下具体的假设，并大致知道什么证据能说明它对不对[^nanda2025process-e5]。

用贯穿全书的例子 `[本项目分析]`：核心结论是"现有大模型漏洞检测的评测结果被数据泄露高估了"；空的结果表是"每个模型、每个工具，去掉泄露合约前后的准确率"；最大风险是"判断合约是否泄露的方法不可靠"，已经手工核对过 50 个样本；导师看过简介，同意先做。四条都过了。

### 判断你要做哪一类研究

出口检查过了，再看你那句话在说什么。它决定了你要做哪一类研究，也决定了第二部分要拿什么证据 `[本项目分析]`：

| 你那句话在说什么 | 研究套路 | 常见的研究类型 | 在目录里找 |
|---|---|---|---|
| 某个现象有多普遍、是什么样 | [观察描述](../05_research-strategies/observe_describe.md) | 实证研究，比如[仓库挖掘研究](../07_fields/computer-science/practices/repository_mining.md)、[问卷调查](../06_methods/questionnaire_survey.md) | [用已有的数据或模型](../06_methods/README.md#用已有的数据或模型)、[涉及人的研究](../06_methods/README.md#涉及人的研究) |
| 已有的几种做法，哪个在什么条件下更好 | [比较评估](../05_research-strategies/compare_evaluate.md) | 比较已有做法，比如[基准评测](../07_fields/computer-science/practices/benchmarking.md)、[对照实验](../06_methods/controlled_experiment.md) | [提出新东西并评估](../06_methods/README.md#提出新东西并评估) |
| 我做出了比已有的更好的东西 | [构建改进](../05_research-strategies/build_improve.md) | 工具或方法论文，见[工程研究](../07_fields/computer-science/practices/engineering_research.md) | [提出新东西并评估](../06_methods/README.md#提出新东西并评估) |
| 过去的测法不准，或者我建了一把新的尺子 | [测量](../05_research-strategies/measure.md) | 基准或数据集，见[基准评测](../07_fields/computer-science/practices/benchmarking.md) | [提出新东西并评估](../06_methods/README.md#提出新东西并评估) |
| 已有研究合起来说明了什么 | [综合](../05_research-strategies/synthesize.md) | 综述，见[综述研究](../06_methods/review_study.md) | [以已发表的研究为材料](../06_methods/README.md#以已发表的研究为材料) |
| 某个因素导致了某个结果 | [解释因果](../05_research-strategies/explain_causality.md) | 比如[对照实验](../06_methods/controlled_experiment.md)、[准实验与因果识别](../06_methods/quasi_experiment.md) | [涉及人的研究](../06_methods/README.md#涉及人的研究)、[用已有的数据或模型](../06_methods/README.md#用已有的数据或模型) |
| 某个结论在给定条件下必然成立 | [证明](../05_research-strategies/prove.md) | 比如[理论研究](../07_fields/computer-science/practices/theoretical_research.md) | [档案、文本与论证](../06_methods/README.md#档案文本与论证) |
| 对一段文本、一项制度或一种思想的新解释 | [解读论证](../05_research-strategies/interpret_argue.md) | 人文社科为主，比如文本细读、规范法学、哲学论证 | [档案、文本与论证](../06_methods/README.md#档案文本与论证) |

所有研究类型的完整目录，按研究者平时的叫法排列，见[研究类型：具体怎么做](../06_methods/README.md)。有几类贡献时怎样分清主次，见[研究套路](../05_research-strategies/README.md#怎样选出主要套路)。

贯穿全书的例子，主要套路是测量：贡献是指出现有评测的测法有问题。其中"泄露有多普遍"那部分属于观察描述，要用仓库挖掘一类的实证做法去数 `[本项目分析]`。

**写下来：** 在一页简介上补两行：四条出口检查各自过了没有；你的主要套路，以及打算做的研究类型。

## 关键判断

**收窄、换角度，还是放弃？** 收敛过程中，你常常会遇到障碍。可以这样判断 `[本项目分析]`：

| 遇到的情况 | 通常的做法 |
|---|---|
| 结论太大，证据要求太高 | 收窄：限定条件、限定对象、把"总是"改成"在某条件下" |
| 核心数据拿不到 | 换角度：看有没有别的证据能支撑同类结论；或者改成另一种套路 |
| 别人已经做了大部分 | 找对方没覆盖的部分，或对方做法里的问题 |
| 想不出谁会在乎 | 回头重新想问题本身，不要硬编一个应用场景 |
| 几轮下来每个候选都站不住 | 回到找问题的阶段，扩大候选范围 |

**什么时候算想清楚了？** 不是"再也想不出问题"，而是一页简介的每一栏都写得出，导师追问时你答得上，而且最没把握的部分已经有了一个试过的小实验。

## 常见错误

| 错误 | 为什么是问题 |
|---|---|
| 用"研究了 X""探索了 X"描述目标 | 只说了活动，没说结果，读者不知道你要证明什么[^shaw2003writing-e18] |
| 先想做什么实验，再想能说明什么 | 实验做完常常发现对论文没用；证据应由结论决定 |
| 结论说得太满 | 需要的证据远超你能拿到的[^shaw2003writing-e16] |
| 做完才查相关工作 | 可能发现别人早已发表[^noble2023ten-e5] |
| 只查文献，不问人 | 漏掉还没发表或刚发表的工作[^eisnerproblems-e9] |
| 可行性只按"理想情况"估 | 纸面上容易的往往实际很难[^alon2009choose-e3] |
| 一页简介写完就不再改 | 想法在变，简介不变，就失去了作用 `[本项目分析]` |
| 一个想法刚觉得可行，就一头扎进去 | 可能追着一个没想清楚的想法跑很久[^noble2023ten-e2] |

## 产出物

- 一页项目简介（第 6 节），以及它的历次修改版本
- 最接近工作的对比表（第 3 节）
- 至少一张空的结果表（第 4 节）
- 一个已经做过的小实验，以及它的结果（第 5 节）
- 出口检查结果：四条各自过了没有，以及你的主要套路和研究类型（第 7 节）

## 检查点

满足下面几条，可以进入下一步：

- [ ] 能用一句话说出核心结论，用的是表示结果的说法
- [ ] 能说出它成立后，谁会因此改变什么
- [ ] 查过文献、问过懂行的人，能具体说出和最接近的三项工作有什么不同
- [ ] 知道审稿人会追问什么，画出了空的结果表
- [ ] 需要的数据、算力、基线都已确认能拿到，或者有了明确的获取办法
- [ ] 最没把握的部分做过小实验，结果没有否定整个想法
- [ ] 导师看过一页简介，没有提出根本性的反对
- [ ] 第 7 节的四条出口检查都过了，并写下了主要套路和研究类型

## 回退信号

| 出现这种情况 | 回到哪里 |
|---|---|
| 写不出具体假设，说不出要什么证据 | [动手探索](03_explore.md)，再做几次小尝试 |
| 小实验否定了核心假设 | 换一个候选：先看[判断和筛选](04_judge-and-screen.md)时留下的其他候选 |
| 所有候选结论都被证明别人做过了 | [生成候选问题](02_generate-problems.md)，再找一轮 |
| 对领域了解太少，判断不了重要性和新颖性 | [进入领域、探索文献](01_enter-a-field.md)，再读一批 |
| 一两个月还在原地转，每轮都推翻上一轮 | 和导师一起定一个，先做起来；纠结本身也是信号 `[本项目分析]` |

## 下一步

出口检查都过了，就进入第二部分。第一步是[从研究问题到证据清单](../02_do-the-project/01_question-to-evidence.md)：把核心结论拆成几个研究问题，把空的结果表展开成一份证据清单，想清楚每样证据要怎样拿到。
