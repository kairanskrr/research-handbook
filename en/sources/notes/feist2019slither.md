# Feist, Grieco & Groce 2019: Slither: A Static Analysis Framework For Smart Contracts

- Source: `feist2019slither`, [arXiv preprint](https://arxiv.org/abs/1908.09878)
- Version: arXiv:1908.09878v1 (August 26, 2019), 8 pages; formally published at WETSEB 2019 (the 2nd IEEE/ACM International Workshop on Emerging Trends in Software Engineering for Blockchain), pp. 8–15. Locations give sections and page numbers in the arXiv version.

### E1

- Location: §I Introduction, p. 1
- Quote: "Often, the deployed smart contract's code is insecure: software vulnerabilities are regularly identified, and have been exploited by malicious actors, resulting in millions of dollars in damages and harm to the reputation of blockchain systems."
- Key point: Deployed smart contract code is often insecure, and its vulnerabilities have been exploited, causing millions of dollars in losses.

### E2

- Location: §I Introduction, p. 1
- Quote: "While modern compilers, such as clang, offer various APIs on top of which third-party analyzers can be built, the Solidity compiler fails to offer the same features. Ideally, a static analysis framework for Ethereum smart contracts should have the following properties:"
- Key point: The authors first name the gap (unlike clang, the Solidity compiler offers no APIs for building analysis tools on top of it), then list the properties a good analysis framework should have.

### E3

- Location: §I Introduction, p. 1
- Quote: "2) Robustness: it should parse and analyze real-world code without crashing. 3) Performance: analysis should be fast, even for large contracts [...] 4) Accuracy: it should allow for the development of detectors that find most potential issues while maintaining a low false positive rate."
- Key point: The properties include robustness (handling real-world code without crashing), performance (fast analysis) and accuracy (finding most issues with few false positives), and the later evaluation compares tools on exactly these.

### E4

- Location: §I Introduction, p. 1
- Quote: "We present Slither, a framework for static analysis of Solidity contracts. We detail the design of Slither's intermediate representation and analyzers. We evaluate and compare the performance, robustness, and accuracy of Slither on a large set of actively used smart contracts."
- Key point: The paper's three contributions: the Slither tool, the design of its intermediate representation and analyzers, and an evaluation comparing its performance, robustness and accuracy with other tools on many real contracts.

### E5

- Location: §III Slither, p. 2
- Quote: "Slither takes as initial input the Solidity Abstract Syntax Tree (AST) generated by the Solidity compiler from the contract source code. In the first stage, Slither recovers important information such as the contract's inheritance graph, the control flow graph (CFG), and the list of expressions. Next, Slither transforms the entire code of the contract to SlithIR, its internal representation language."
- Key point: Slither works in stages: it reads the abstract syntax tree produced by the compiler, recovers the inheritance graph and control flow graph, then converts the code into its own intermediate representation, SlithIR, for analysis.

### E6

- Location: §V-A Vulnerability Detection Evaluation, p. 5
- Quote: "We compare Slither (release 0.5.0) with other open-source static analysis tools to detect vulnerabilities in Ethereum smart contracts: Securify (revision 37e2984), SmartCheck (revision 4d3367a) and Solhint (release 1.1.10). We decided to focus our evaluation exclusively on tools' reentrancy detectors, since reentrancy is one of the oldest, most well understood, and most dangerous security issues."
- Key point: The evaluation compares Slither with three open-source static analysis tools, giving the exact version of each, and compares only the reentrancy detectors that all of them have.

### E7

- Location: §V-A1 Experiments, pp. 5–6
- Quote: "In the second experiment, we used the 1000 most used contracts (those with the largest number of transactions), for which Etherscan provides the source code."
- Key point: The second experiment used the 1,000 contracts with the most transactions whose source code is available on Etherscan.

### E8

- Location: §V-A1 Experiments, p. 6
- Quote: "However, we found that such a selection is biased in an unhelpful way, as most of the contracts deployed on Ethereum are essentially tests, lacking the complexity (and code quality) that widely used contracts have."
- Key point: The authors explain why they did not simply sample contracts from the chain: most deployed contracts are just tests and lack the complexity of widely used ones.

### E9

- Location: §V-A2 Metrics, p. 6
- Quote: "The tools are evaluated on three metrics: performance, robustness, and accuracy. [...] The robustness metric indicates how often each tool fails to parse, decompile, or analyze a smart contract. Finally, the accuracy metric measures both number of contracts flagged and number of false positives detected."
- Key point: The comparison uses three predefined metrics: performance, robustness (how often analysis fails) and accuracy (contracts flagged and false positives).

### E10

- Location: §V-A4 Experiment 1, p. 6
- Quote: "However, we consider the result valid only if the tool can detect the actual reentrancy that was used during the exploitation of the contract. Slither is the only tool capable of finding these two real-world cases of reentrancy."
- Key point: On the DAO and SpankChain, two contracts that were actually attacked, only Slither found the reentrancy vulnerability that was really exploited.

### E11

- Location: §V-A5 Experiment 2, p. 6
- Quote: "Slither failed only for 0.1% of the contracts, while Solhint failed for around 1.2%. SmartCheck and Securify are less robust, failing 10.22% and 11.20% of the time, respectively."
- Key point: On robustness, Slither failed on only 0.1% of contracts, against about 1.2% for Solhint, 10.22% for SmartCheck and 11.20% for Securify.

### E12

- Location: §V-A5 Experiment 2, p. 6
- Quote: "Due to time constraints, we manually reviewed a random sample of at least 50 of the flagged contracts for each tool, rather than all potentially benign reentrancies. Our experiments show that Slither is the most accurate tool, with the lowest false positive rate: 10.9%, followed by Securify with 25%. SmartCheck and Solhint have high false positive rates of 73.6% and 91.3% respectively."
- Key point: The authors manually checked a random sample of at least 50 flagged contracts per tool; Slither had the lowest false positive rate (10.9%), against 25% for Securify, 73.6% for SmartCheck and 91.3% for Solhint.

### E13

- Location: §V-A6 Discussion, p. 6
- Quote: "However, we should note that our experiments are limited in many ways. The false positives rate for Securify is based on a very low number of findings (8). Additionally, several contracts in our dataset share fragments of code, creating a bias in the results."
- Key point: The authors acknowledge limits: Securify's false positive rate rests on only 8 findings, and many contracts in the dataset share code fragments, which biases the results.

### E14

- Location: §V-D Threats to Validity, p. 7
- Quote: "The most important threat to validity is that our primary experiment is limited to reentrancy detection over a limited set of contracts. The measure we used to determine a meaningful set of contracts (number of transactions) is reasonable, but not standardized by the community."
- Key point: The main threat to validity is that the primary experiment covers only reentrancy detection on a limited set of contracts, and choosing contracts by transaction count is not a community standard.

### E15

- Location: §I Introduction, p. 2; §V-D Threats to Validity, p. 7
- Quote: "Both Slither and our dataset are open source, so that others can validate and improve on our results." / "In order to make our results reproducible, and allow checking of our code and analysis methods, we have made our experimental setup available."
- Key point: The tool and dataset are open source and the experimental setup is public, so others can reproduce and check the results.
